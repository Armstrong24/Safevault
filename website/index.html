Scope and limitations

Synthetic files only, not real student data. Scheduling runs only while the laptop and WSL are on. Governance retention can be bypassed by a specially authorised administrator; Compliance mode was not used. Recovery runs on the same laptop with a separate read-only identity; production would restore on a separate clean machine. Auto-refresh is periodic polling. Ransomware-resilient under the tested threat model, not ransomware-proof.

Architecture

How SafeVault works

Ransomware encrypts files and then tries to delete the backups. SafeVault keeps older clean versions out of the attacker's reach and proves they can be restored.

Three layers of defence

01 · LEAST PRIVILEGEA stolen key can't destroy backups

The laptop's uploader can only add new objects. Read, list, delete and retention changes are explicitly denied.

02 · IMMUTABILITYOld versions stay put

Versioning keeps every version, and Object Lock (Governance, 7 days) blocks deletion of retained versions.

03 · PROVEN RECOVERYBackups are tested

A clean version is restored from S3 and every file is checked against an independent SHA-256 baseline.

Key terms

S3 Versioning

Every upload creates a new version; earlier versions remain retrievable.

Object Lock (WORM)

Write-once-read-many retention that blocks deleting a version until its date passes.

Governance vs Compliance

Governance can be bypassed by a special permission; Compliance cannot, even by root.

SHA-256 baseline

Fingerprints of clean files saved separately, used to prove the restore is exact.
